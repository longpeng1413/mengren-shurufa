# v0.3.7 私密投递与提示交互问题分析

> 后续状态：2026-11-07 用户已授权发布 v0.3.8 供真实设备测试。下文保留开发阶段的检查与历史反馈；发布说明见 [v0.3.8](../../mengren/releases/v0.3.8.md)。

2026-11-07。状态：用户真机反馈未通过，已核查代码；后续用户已授权本地优化开发，尚未发布新版。当前代码变更与复测边界见 [私密互传设计](../design/private-transfer.md)；下列原始缺陷分析保留用于对照。以下区分确定缺陷、待定位故障与拟议设计，不能将拟议设计当作现有能力。

## 用户事实

- 魅族手机复制密码后，华为手机与电脑均未收到可用内容。
- 电脑私密输入快捷键没有填入，反复出现准备等待、取消或过期提示。
- 多次按键后提示仍陆续出现，用户无法判断是否发送、是否接收、是否过期。
- 此前手机到电脑曾获用户确认，不足以覆盖本次版本、设备组合和新增交互。

## 已从源码确认的设计与实现问题

| 问题 | 代码依据 | 对使用的影响 |
| --- | --- | --- |
| 输入键在空槽时自动进入等待，再按又取消 | `apps/clipboard/src/system/windows/private/mod.rs` 的 `input_or_wait` 与 `automation.rs` 的 `prepare`；Android `PrivateReceive.input` 同类切换 | 想输入的按键变成隐式准备/取消，操作本身不能证明接收成功 |
| 焦点改变、禁收和真正超时共用原因 | `automation.rs` 在同一分支发 `private.wait_cancelled`，中文为“取消或过期” | 即使未收到内容或未等两分钟，也看起来像密码过期 |
| 每次动作直接提交系统提示 | Windows `listener::notice → tray::notice → Shell_NotifyIconW(NIF_INFO)`；Android 直接创建 Toast | 没有产品级去重、限频或按会话替换；系统展示时序可与当前状态脱节，与用户描述一致。不是已确认存在模态 MessageBox 阻塞 |
| 手动输入缺少统一的正在输入保护 | Windows `input()` 在 `pending()` 之后每次创建线程，消费发生在等待修饰键释放之后 | 重复触发可让多个线程争同一槽，后到者再报“没有内容/已使用或过期”；应由单一控制器处理 |
| 源端在尝试发送前标记该复制已见 | Android `ClipboardWatcher.capture → firstSeen` 在 `PrivateSend.automatic` 前持久化时间戳 | 若第一次未成功，重新弹出键盘不会把同一复制重新当新事件。去重不等于投递成功，失败必须明确且支持显式重发，不引入秘密离线队列 |
| 发送结果缺少逐目标原因 | shared `send_once` 合并为成功数量或 `PrivateFailed`；Android 展示丢弃成功数量，Windows 也只给通用成功/失败 | 无法知道华为和电脑各自是否在线、允许接收、已确认入槽或输入失败；至少一台成功不能写成全部已到 |
| JNI 启动任务与接收确认不是一件事 | `clipboardSyncPrivateSend` 的布尔结果对应后台发送是否受理，最终结果走同步事件 | UI 必须区分已开始、目标收到与已经填入，不能用任务已启动推导密码已送达 |

以上足以判断应先修改交互，不应要求用户重新完成一套测试来证明问题。系统通知实际排队顺序、具体机型系统限制尚未复现，不将静态审查写成真机复现。

## 魅族没有送达的根因尚未确定

当前不能断定是敏感标记、输入法捕获时机、服务未就绪、权限/锁屏状态、直接配对关系、局域网地址或中转连接中的哪一步失败。需要逐段观察无正文的状态：

1. 是否收到新的剪贴板事件、能否读取文字、是否存在受支持的敏感标记。
2. 自动发送是否启用、同步服务是否可用、发送任务是否受理。
3. 对每个直接配对目标，是否可连接及允许私密接收。
4. 对端是否认证并确认内容进入内存槽。
5. 填入是否尝试、目标是否仍有效、系统是否接受提交。

不得通过打印密码、密码摘要、长度预览、真实令牌或持久化秘密来诊断。非秘密的随机操作标识只在内存关联当前投递；诊断只记录阶段、结果码和设备别名或脱敏编号。没有敏感标记时不按文字外观猜密码。

## 原拟议方案（已被后续决定取代）

用户已确定复制后自动发送、自动接收、按需填入；本地代码已移除准备等待入口，而非保留独立等待。下文仅为原方案记录，不作为当前操作说明。

### 将输入与等待分开

- 私密输入快捷键只处理已收到内容。空槽时不启动等待、不清空系统剪贴板、不创建后台输入线程；至多更新一条“尚未收到私密内容”的状态。
- 等待一次保留为独立、明确的操作，不再藏在“粘贴”按键背后。反复触发等待应保持同一个等待会话，取消使用独立动作；不靠反复切换状态表达取消。
- 密码框自动填入仍是目标功能，但必须以对端真实接收事件为前提；没有接收确认不能宣称已可填入。普通字段仍需明确选择，不猜目标。

### 用一个当前状态替代通知队列

- 当前状态区分未收到、等待一次、已收到、正在输入、已输入、已失效、发送/输入失败。
- 同一会话只有一个状态所有者、一个输入任务和一个内存槽。重复快捷键在输入期间忽略，不能创建多个消费线程或多个相同提示。
- 常规准备、取消和重复按键不投递系统气泡或 Toast；界面只展示当前状态。确需错误提醒时合并、限频，并在展示前检查是否仍属于当前会话。
- 等待超时、已收内容过期、焦点变化取消分别给出准确原因，不用一条“取消或过期”笼统解释。

### 先送达，再报告填入结果

- 发送端按目标显示发送中、对端已收到、目标拒收/离线/认证或网络失败。失败提供显式重发，不自动保存或补发秘密。
- 接收确认仅表示入内存槽；输入成功另记本地结果，不能混成“已发送/已自动填入”。若之后需要向源端反馈填入结果，先设计无正文的认证确认，不把它当作现有协议能力。
- 手机通过键盘当前状态显示已收到及点击填入，电脑通过非抢焦点状态显示；均不暴露密码正文。

## 后续开发与验收顺序

1. 先做共享交互状态、输入单任务和通知去重；覆盖空槽连续按键、已有内容连续按键、快速取消/切换焦点、迟到事件不能恢复旧状态。
2. 增加每个接收端的脱敏投递阶段，区分捕获、任务受理、到达和填入；定位本次魅族到两端的真实断点。
3. 确认接收端直接配对关系以及两端能力协商，不让普通历史经第三台转发的可用性冒充私密直投可用。
4. 定向复测“魅族复制一次 → 华为收到 → 点击/自动填入”和“魅族复制一次 → 电脑收到 → 只按一次输入”，再回归其他方向与锁屏/过期规则。
5. 原安全约束继续：不进普通历史、不写接收端系统剪贴板、不离线补发、失败不回退粘贴。当前不要求用户再测，不发布新版；后续按用户指示合并验证后的修复。
